> **프로젝트**: Univ_Admissions_Search (거북스쿨 입시 검색 서비스)
> **작성일**: 2026-06-29
> **상태**: 초안 (v0.1) — 검토/수정 필요

---

## 0. 한눈에 보기

본 서비스는 **수시·정시 전형 데이터를 통합 검색**하고, 사용자의 **생기부·성적·각 앱 분석결과를 종합한 맞춤 AI 조언**까지 제공하는 입시 검색·상담 앱이다. **고1~고3 전체**(2015·2022 교육과정 모두)를 대상으로 한다.

- **인증**: Hub(통합 SSO)에서 로그인/계정 관리
- **검색 대상 데이터**: 수시앱(susi)·정시앱(jungsi) 전형 DB → **multiSchema 직접 읽기**
- **개인화 입력 데이터**: 생기부 + 모의고사 성적 + 4개 앱(수시/정시/생기북/모고) 분석결과 → **Hub "입시 프로파일" API**로 수신
- **핵심 가치**: 키워드·AI 시멘틱 검색 + 통합 프로파일 기반 **맞춤 추천·AI 조언**
- **멀티앱 구조**: 본 검색앱과 별도로 "맞춤 입시정보 배달앱"이 같은 **개인화 레이어(Hub API)** 를 공유 (§2.5)
- **인프라**: GCP (백엔드 NestJS, 프론트엔드 React+Vite, Cloud SQL PostgreSQL)

## 1. 서비스 개요

### 1.1 목적
대학 입시(수시·정시)의 방대한 전형 정보를 한 곳에서 검색하고, 자연어 질의로 "내 조건에 맞는 전형"을 찾을 수 있게 한다.

### 1.2 문제 정의
- 전형 정보가 대학·전형유형별로 흩어져 있어 비교가 어렵다.
- 사용자는 "내신 2등급, 수도권 컴공, 면접 없는 수시" 같은 **복합·자연어 조건**으로 찾고 싶지만 기존 검색은 정형 필터만 지원한다.
- 수시(학생부/논술/실기 등)와 정시(수능 위주)의 데이터 구조가 달라 통합 검색이 까다롭다.

### 1.3 타깃 사용자
- **고1~고3 전체** 및 N수생, 학부모 (2015 교육과정=현 고3, 2022 교육과정=현 고1~2)
- 진학 상담 교사 / 입시 컨설턴트

### 1.4 핵심 기능 (요약)
| 구분 | 기능 |
|------|------|
| 인증 | Hub SSO 로그인, 권한(역할) 관리 |
| 검색 | 키워드 검색, 정형 필터, **AI 시멘틱 검색** |
| 전형 | 수시·정시 전형 통합 조회, 상세 보기, 비교 |
| **맞춤 추천** | 통합 프로파일(생기부+성적+분석) 기반 적합 전형 추천 |
| **AI 조언** | 프로파일 + 후보전형 근거로 맞춤 입시 조언 생성(RAG) |
| 개인화 | 즐겨찾기/스크랩, 최근 검색 |
| 운영 | 전형 데이터 동기화, 검색 로그/분석 |

### 1.5 데이터 범위 (교육과정)
- **2015 개정 교육과정** — 현 고3 (~2027학년도 수능 체계)
- **2022 개정 교육과정** — 현 고1~2 (2028학년도 수능~, 통합형). DB 미완성 → 단계적 채움.
- 검색앱은 **두 교육과정 공존**을 전제로 설계(전형·성적분석을 `curriculum` 플래그로 분기, 데이터 없으면 graceful 처리). 교육과정 과목 체계는 Hub `hub_2015_kyokwa_subject` / `hub_2022_kyokwa_subject` 참조.

## 2. 시스템 아키텍처

### 2.1 전체 구성
```
   ┌───────────────────────────────────────────────────────────┐
   │  Hub (통합 인증/SSO + 개인화 레이어 소유)                      │
   │   - 계정/로그인/권한, JWT 발급(토큰교환)                       │
   │   - 생기부 업로드 보관                                         │
   │   - ★ "입시 프로파일" 내부 API  (GET /api/internal/users/:id/admission-profile) │
   │        ↳ 생기부+성적+4개앱 분석결과를 종합해 제공               │
   └───────┬───────────────────────────────────────────┬─────────┘
           │ 분석결과 수집(Hub가 소유)                     │ 프로파일 제공(ServiceAuth)
   ┌───────┴────────┬──────────┬──────────┐       ┌──────┴──────┬───────────────┐
   ▼                ▼          ▼          ▼       ▼             ▼
 susi(수시분석)  jungsi(정시분석) 생기북(생기부분석) 모고(모의분석)  검색앱(본 앱)   정보배달앱(별도)
                                                  │ 전형 데이터는 검색앱이 직접 읽음
                                                  └── multiSchema(susi/jungsi 전형) → search 스키마 색인
                              ── 전부 같은 Cloud SQL: geobukschool_prod ──
```
**두 갈래의 데이터 경로(중요)**:
- **전형 데이터**(검색 대상): 검색앱이 `susi`/`jungsi` 전형 테이블을 **multiSchema 직접 읽기** → `search` 스키마 색인. (성능·비용 우위, §2.4)
- **사용자 프로파일**(개인화 입력): **Hub가 소유**하고 내부 API로 제공. 검색앱·배달앱은 소스(생기북/모고 등)를 직접 읽지 않고 Hub의 깨끗한 계약만 소비. (일관성·결합도 우위, §2.5)

### 2.2 검색 서비스 내부 구조
```
[Frontend]  ts-front-479305
  - 검색 UI, 결과/상세/비교, 로그인 리다이렉트(Hub)

      │ HTTPS / JWT
      ▼
[Backend]   ts-back-nest-479305  (NestJS)
  - Auth 모듈      : Hub 토큰 검증, 세션
  - Search 모듈    : 키워드 + 필터 + 시멘틱 쿼리 오케스트레이션
  - Admission 모듈 : 전형 조회/상세/비교
  - AI 모듈        : 임베딩 생성, 벡터검색, LLM 질의해석
  - Sync 모듈      : 수시/정시 전형 데이터 수집·정규화·인덱싱

      │
      ▼
[Data] Cloud SQL  geobuk-db / geobukschool_prod
  - 정규화된 전형 테이블 + 검색 인덱스 + 임베딩 벡터(pgvector*)
```
> *DB는 **PostgreSQL 확정** → `pgvector` 확장으로 벡터검색을 같은 DB에서 처리.

### 2.3 데이터 흐름
1. **수집(Sync)**: 수시앱(`susi` 스키마)/정시앱(`jungsi` 스키마)의 전형 데이터 → 검색앱의 `search` 스키마로 수집·인덱싱. (연동 방식 비교는 §2.4)
2. **정규화**: 수시/정시의 상이한 스키마를 공통 전형 모델로 변환.
3. **인덱싱**: 검색용 텍스트 인덱스(FTS) + 임베딩 벡터(pgvector) 생성·저장.
4. **검색**: 사용자 질의 → (키워드/필터 + 시멘틱) 하이브리드 검색 → 랭킹 → 결과.

### 2.4 수시·정시앱 데이터 연동 방식 (3가지 비교)

> **중요 전제**: 거북스쿨 전 앱은 **하나의 Cloud SQL PostgreSQL을 스키마로 격리해 공유**한다. 즉 susi/jungsi 전형 데이터는 검색앱과 *물리적으로 같은 DB 안*(`susi`/`jungsi` 스키마)에 있다. 이 점이 연동 방식 선택을 크게 좌우한다.

**① DB 직접 읽기 (cross-schema, Prisma multiSchema)**
- 방식: 검색앱 Prisma datasource에 `susi`/`jungsi` 스키마를 추가하고 **읽기 전용**으로 직접 조회 → `search` 스키마에 정규화·인덱싱.
- 장점: 같은 DB라 추가 인프라 0, 구현 가장 빠름, 대량 초기 인덱싱에 최적.
- 단점: 상대 앱 테이블 구조에 강결합(그쪽이 스키마 바꾸면 깨짐), 읽기 전용 규율 필요(`DB_SYNCHRONIZE=false`는 이미 강제됨).
- 적합: **초기 구축 + 주기적 배치 동기화**.

**② API 호출 (내부 엔드포인트 + 서비스 토큰)**
- 방식: susi/jungsi 백엔드가 노출하는 `/api/internal/*` 전형 엔드포인트를 `ServiceAuthGuard`(`AUTH_SERVICE_SECRET` + `X-Service-Id`)로 호출해 데이터 수신. (생태계가 이미 쓰는 Hub↔Mogo 패턴과 동일)
- 장점: 소유권 경계 존중(느슨한 결합), 상대 앱이 응답 포맷 안정화 책임, 깨끗한 계약.
- 단점: 상대 앱이 **벌크 조회용 내부 엔드포인트를 새로 만들어야** 함, 네트워크 지연.
- 적합: 경계를 명확히 하고 싶을 때, 중규모 동기화.

**③ Pub/Sub 이벤트 (변경 스트리밍)**
- 방식: susi/jungsi가 전형 생성/수정 시 이벤트 발행 → 검색앱이 구독해 인덱스 증분 갱신.
- 장점: 최신성 최고, 완전 디커플링, 확장성 우수.
- 단점: 인프라/복잡도 최고, 상대 앱이 **이벤트 발행 로직을 새로 구현해야** 함(현재 없음).
- 적합: 실시간성이 중요해지는 후기 단계.

**권장(단계적)**: 1단계는 **① 직접 읽기(읽기 전용)로 배치 동기화** — 데이터가 같은 DB라 가장 저비용·저위험. 검색 시점엔 상대 스키마를 라이브로 안 건드리고 검색앱의 `search` 스키마/벡터인덱스만 조회하므로 쿼리 단계는 이미 디커플링됨. 이후 최신성이 필요해지면 **③ Pub/Sub 증분 갱신**을 추가. ②는 상대 앱이 내부 API를 제공할 의향이 있을 때 1↔3 사이의 절충안.

#### ①(multiSchema 직접 읽기) vs ②(내부 API) — 성능·비용 비교

데이터가 **같은 DB 인스턴스 안**(스키마만 다름)이라 경로 차이가 곧 성능·비용 차이가 된다.
```
① multiSchema: search-backend ──SQL──► PostgreSQL                (DB 왕복 1회)
② 내부 API:    search-backend ──HTTP──► susi-backend ──SQL──► PostgreSQL
                                          (네트워크 2홉 + 직렬화 + 백엔드 1개 추가)
```

| 항목 | ① multiSchema | ② 내부 API |
|------|--------------|-----------|
| 단건 지연 | DB 쿼리시간만 (보통 한 자릿수 ms) | + HTTP/TLS/JSON 직렬화 + App Engine 홉 (수십 ms↑) |
| 대량 동기화 | `SELECT…JOIN` 한 번에 스트리밍, COPY 가능 | 페이지네이션 N회 호출 → N×오버헤드 |
| 10만 건 인덱싱(예시) | 단일 쿼리, 수 초 | 페이지 500개씩 200회 → 수십 초~분 |
| 병목 | DB·search-backend 커넥션 | susi-backend 인스턴스 수/동시성 |
| Cloud SQL 비용 | 동일(같은 DB 1개 쿼리) | 동일하되 susi-backend가 한 번 더 쿼리 |
| App Engine 비용 | search-backend만(동기화 시) | **+ susi/jungsi backend 인스턴스 시간(직렬화 CPU, autoscale)** |
| 네트워크 egress | ~0 (동일 리전) | ~0 (동일 리전) |
| 개발/유지 | 검색앱 Prisma 설정만 | susi/jungsi에 벌크 내부 API **신규 개발+유지** |
| 결합도 | 상대 스키마에 강결합(읽기전용·sync잡만 영향) | 느슨(API 계약만 유지하면 됨) |

**결론**: 순수 성능·비용은 **① multiSchema가 더 빠르고 더 저렴**(같은 DB라 당연). ②의 유일한 우위는 결합도. 동기화는 배치성이고 검색은 자기 `search` 스키마만 조회하므로, **①로 진행하되 강결합 리스크를 권한 분리·통합테스트로 완화**하는 것이 최적 균형. → 실행계획은 [`데이터연동-multiSchema-계획.md`](./데이터연동-multiSchema-계획.md) 참조.

### 2.5 멀티앱 구조 & Hub 개인화 레이어 (확정: Hub API 소유)

검색앱과 **별도로 "맞춤 입시정보 배달앱"**(사용자 성적·상황에 맞는 최신 입시정보를 푸시)이 기획 중이다. 두 앱의 **콘텐츠 엔진은 서로 다르다**:
- 검색앱 엔진: 내부 *전형 DB* 색인 + 시멘틱 검색 (Pull)
- 배달앱 엔진: *외부 최신 입시정보*(모집요강 변경·일정·정책·뉴스 등) 수집·큐레이션 + 푸시 (Push)

그러나 **개인화(사용자 통합 프로파일 + 매칭) 레이어는 공유**된다. 이 공유 레이어는 **Hub가 소유**하고 내부 API로 제공한다(결정 2026-06-29).

```
 검색앱 엔진 ──┐                              ┌── 배달앱 엔진
 (전형 색인)   │                              │   (외부 입시정보 수집·푸시)
              └──► [Hub: 입시 프로파일 API] ◄──┘
                   생기부+성적+4앱 분석 통합 (한 곳에서 계산)
```
- **Why Hub 소유**: Hub는 이미 SSOT이고 생기부를 보유. 소스(susi/jungsi/생기북/모고)를 읽는 주체를 Hub 하나로 모아 → 로직 일관성↑, 다른 앱의 결합/권한↓. 소비 앱은 깨끗한 계약만 사용.
- **승격 경로**: 향후 프로파일 로직이 복잡해지면 그대로 유지, 단순 단계에선 캐싱으로 성능 보강.
- **검색앱이 Hub에 의존하는 범위**: 전형 데이터는 검색앱이 직접(multiSchema), **프로파일만 Hub API**.

> Hub 측 신규 작업: `GET /api/internal/users/:hubUserId/admission-profile` (ServiceAuthGuard, `X-Service-Id`) 구현. 상세는 §4.5.

## 3. 데이터 모델 (전형 DB)

SSO 연동은 [`Hub-SSO-연동.md`](./Hub-SSO-연동.md).

### 3.1 핵심 엔티티
- **University(대학)**: 대학 기본정보(지역, 설립유형, 캠퍼스 등)
- **Department(학과/모집단위)**: 계열, 학과명, 정원
- **Admission(전형)**: 전형의 핵심 — 수시/정시 공통 상위 모델
- **AdmissionRequirement(전형요소)**: 학생부/내신/수능/논술/면접/실기 반영 비율 등
- **AdmissionStat(입결/통계)**: 연도별 경쟁률, 충원율, 합격선(가능 범위)
- **Embedding(벡터)**: 전형 설명 텍스트의 임베딩

### 3.2 Admission(전형) 공통 모델 (예시)
| 필드 | 설명 |
|------|------|
| `id` | PK |
| `university_id` | 대학 FK |

## 4. AI 시멘틱 검색 설계

### 4.1 목표
"내신 2등급대, 면접 없는 수도권 컴퓨터공학과 수시" 같은 **자연어 질의**를 이해하고 적합한 전형을 반환.

### 4.2 파이프라인 (하이브리드 검색)
```
사용자 자연어 질의
   │
   ├─(1) 질의 해석(LLM)  → 구조화 필터 추출 {지역, 계열, 등급, 면접유무, 트랙...}
   │
   ├─(2) 임베딩 생성     → 질의 벡터
   │
   ├─(3a) 정형 필터 검색  (SQL: 지역/계열/트랙/조건)
   ├─(3b) 시멘틱 벡터 검색 (코사인 유사도 Top-K)
   │
   ├─(4) 하이브리드 랭킹  (필터 결과 ∩/가중합 + 유사도 + 인기/입결 가중치)
   │
   └─(5) (선택) LLM 결과 요약/근거 설명
```

### 4.3 구성 요소 선택지
- **임베딩 모델**: Vertex AI `text-embedding`(GCP 친화) 또는 OpenAI `text-embedding-3` 등. (한국어 성능 검증 필요)
- **벡터 저장/검색**: PostgreSQL + `pgvector`(권장, 단일 DB) / Vertex AI Vector Search / Qdrant.
- **LLM(질의해석·요약)**: Vertex AI Gemini 또는 OpenAI. 비용·지연·한국어 품질로 결정.
- **랭킹**: 1차 벡터 Top-K → 정형조건 부합도·입결 적합도·최신성으로 재정렬(re-rank).

### 4.4 품질·안전 고려
- 합격 가능성/합격선은 **추정치이며 보장 아님**을 항상 명시(입시 정보 특성상 책임소재 주의).
- 환각 방지: LLM은 DB에 존재하는 전형만 인용(RAG, 출처 ID 포함).
- 데이터 최신성: 학년도/모집요강 개정 반영 주기 관리.

### 4.5 개인화 데이터 통합 & 맞춤 AI 조언

#### Hub "입시 프로파일" API (개인화 입력의 단일 소스)
검색앱은 사용자 성적/분석 데이터를 직접 모으지 않고 **Hub의 통합 프로파일 API 하나만 호출**한다.
`GET /api/internal/users/:hubUserId/admission-profile` (ServiceAuth, `X-Service-Id: search`)

Hub가 종합하는 입력(전부 같은 Cloud SQL):
| 입력 | 출처 앱 | 비고 |
|------|---------|------|
| 생기부 원본 | **Hub** | 업로드 파일 보관처 |
| 생기부 분석 | 생기북(Saenggi-Book) | ✅ 확인됨(`backend/`, **`saenggiview` 스키마**). 핵심: `sv_ai_evaluation`(AI 사정관 평가: 학업/진로/공동체 점수·`summary`·`strengths`/`weaknesses`/`advice` JSON), `sv_ai_timeline`. 생기부 원자료: `sv_subject_learning`(교과/내신: 석차·표준편차·원점수), `sv_select_subject`(선택과목 성취도), `sv_attendance`(출결), `sv_volunteer`(봉사), `sv_sport_art`. 사용자키 `sv_auth_member.hub_member_id`(=hub `auth_member.id`), sv_* 테이블은 `member_id` VarChar(30) 직접 보유 |
| 모의고사 성적·분석 | 모고(Mogo) | ✅ 확인됨(`mogo-backend`, 접두사 `mg_`). 핵심: `mg_student_scores`(과목별 표준점수/백분위/등급/합/누적상위%), `mg_mock_exams`, `mg_student_answers`(오답분석), `mg_student_targets`(목표학과). 사용자키 `mg_auth_member.member_id`=Hub `auth_member.id` |
| 수시 성적분석(교과/내신 합격예측) | susi | `ss_user_*`, `susi_comprehensive_tb`, `susi_pass_record_tb` |
| 정시 성적분석(수능 환산/위험도) | jungsi | `js_user_input_scores`, `js_user_calculated_scores`, `js_user_recruitment_scores` |
| 교육과정 구분 | Hub / Mogo | `hub_2015/2022_kyokwa_subject`. Mogo가 **year/grade로 2015·2022 분기**(`mg_..._2015`/`_2022`)하는 패턴 그대로 차용 가능 |

응답(통합 프로파일) 예시 필드: `curriculum(2015/2022)`, `grade(고1~3)`, `naesin_summary`, `csat_mock_summary`, `saenggibu_summary`, `susi_fit_signals`, `jungsi_fit_signals`.

> **교육과정 매핑 단서(Mogo 확인)**: Mogo는 학생의 `year`/`grade` 기준으로 2015(현 고3, ~2027수능)·2022(현 고1~2, 2028수능~)를 분기한다. 검색앱의 `curriculum` 플래그도 동일 기준을 따르면 됨(현재 sync의 `Y2015` 하드코딩을 이 규칙으로 대체).

#### 맞춤 AI 조언 파이프라인
```
1. 사용자 식별 (Hub JWT memberId)
2. Hub 프로파일 API 호출 → 통합 입시 프로파일 로드
3. 후보 전형 매칭: 프로파일 조건(내신/수능/계열/지역) + 시멘틱 검색(§4.2)
4. 적합 신호 반영: 각 앱이 산출한 분석값(susi 합격예측, jungsi 위험도) 인용 — 재계산 아님
5. LLM(Vertex Gemini) RAG: 프로파일 + 후보전형 근거 → 맞춤 조언 생성(출처 전형 인용)
6. 출력: 추천 전형 + 근거 + 주의(추정치·보장 아님 명시)
```
- 검색앱의 역할은 **재계산이 아니라 종합·설명**: 합격예측 등 무거운 분석은 각 앱이 한 값을 인용한다.
- 교육과정(2015/2022)에 따라 매칭·조언 로직 분기.

## 5. 기술 스택 (확정 — 거북스쿨 생태계 표준 준수)

> 출처: `withjoono/Hub`의 CLAUDE.md(생태계 SSOT) 및 `withjoono/jungsi` CLAUDE.md. **모든 위성앱이 React 18 + Vite / NestJS + Prisma / 공유 PostgreSQL(스키마 격리)로 통일**되어 있으며, 검색앱도 이를 그대로 따른다.

| 영역 | 확정 | 비고 |
|------|------|------|
| 프론트엔드 | **React 18 + Vite** | 생태계 표준. TanStack Router + Zustand + TanStack Query. 패키지매니저 **npm** |
| 백엔드 | **NestJS 10 (TypeScript)** | App Engine service명 예: `search-backend`. 패키지매니저 **yarn** |
| ORM | **Prisma** | TypeORM은 2026-03 생태계에서 제거됨. `multiSchema` preview 사용 |
| DB | **Cloud SQL PostgreSQL** | 단일 공유 인스턴스 `geobuk-db` / `geobukschool_prod`. 검색앱 전용 **스키마 `search`** 사용 |
| 벡터검색 | **PostgreSQL + pgvector** | 같은 DB에서 벡터검색 처리(추가 인프라 불필요). 규모 커지면 Vertex Vector Search 분리 |
| 인증 | **Hub SSO (JWT, HS512, Base64 secret)** | Backend Token Exchange flow(sso_code→verify-code). `DB_SYNCHRONIZE=false` 필수 |
| AI | **Vertex AI** | Gemini(질의해석·요약) + text-embedding(임베딩). GCP 통합 |
| 배포 | **백엔드 Google App Engine**(`ts-back-nest-479305`) / **프론트 Firebase Hosting**(전용 site) | GitHub Actions on push to `main`. Firebase는 `--only hosting:<자기-target>` 강제 |
| 운영 | Cloud Logging, (선택) Pub/Sub | 동기화 이벤트, 검색 로그 |

### 5.1 생태계 정합성 규칙 (반드시 준수)
- 공유 DB이므로 **`DB_SYNCHRONIZE=false`** — 켜면 다른 앱 테이블 드롭 위험.
- 검색앱은 **자기 스키마(`search`)** 안에만 테이블 생성. 테이블 prefix 관례 권장(예: `srch_`).
- **JWT secret 포맷(Base64 + HS512) 절대 변경 금지** — 변경 시 전 생태계 세션 무효화.
- Firebase 배포는 항상 `--only hosting:<자기-target>` (target 생략 시 다른 앱 site 덮어쓰는 사고 이력 있음).
- 서비스간 호출은 `AUTH_SERVICE_SECRET` + `ServiceAuthGuard` + `X-Service-Id` 헤더 (`/api/internal/*`).

### 5.2 프레임워크 선택 근거 (Next.js / Vue 검토 결과)
- **React(Vite) 채택**: 생태계 전 앱이 동일 스택 → 공용 패키지(`geobuk-shared`), SSO helper, 컨벤션, CI/CD를 재사용 가능. **혼용은 기술적으로 가능**(각 앱 독립 배포)하나, 유지보수·인력·코드재사용 측면에서 통일이 유리.
- **Next.js 미채택**: SSR/SEO 장점은 있으나 생태계에 도입 사례 없음 → 빌드/배포 파이프라인(App Engine+Firebase, Vite proxy)·SSO 패턴을 새로 만들어야 함. 검색앱은 로그인 기반 내부 서비스 성격이 강해 SSR 이점이 결정적이지 않음.
- **Vue/Nuxt 미채택**: 생태계와 완전히 이질적 → 공용 코드·노하우 전부 단절. 도입 이점 없음.
