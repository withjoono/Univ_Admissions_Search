## ① susi / jungsi DB 읽기 권한 부여 (multiSchema 직접 읽기 전제)

검색앱은 같은 Cloud SQL의 `susi`·`jungsi` 스키마를 **읽기 전용**으로 조회한다. 이를 위해 전용 읽기 계정에 SELECT 권한이 필요하다.

- **누가 실행?** `geobukschool_prod`의 슈퍼유저(`tsuser`) 또는 각 스키마 소유자.
- **어디서?** Cloud Shell:
  `gcloud sql connect geobuk-db --user=tsuser --database=geobukschool_prod --project=ts-back-nest-479305`
- **순서**: 반드시 **dev(`geobukschool_dev`)에서 먼저 테스트 → prod 적용**.

```sql
-- 1) 검색앱 전용 읽기 계정 생성 (비밀번호는 안전하게 보관)
CREATE USER search_app WITH PASSWORD '<강한-비밀번호>';

-- 2) 검색앱 소유 스키마 (검색앱이 자기 테이블을 만들 곳)
CREATE SCHEMA IF NOT EXISTS search AUTHORIZATION search_app;

-- 3) susi / jungsi 스키마: 읽기 전용만 부여  (대학 ss_university도 susi에 있어 함께 커버됨)
GRANT USAGE ON SCHEMA susi, jungsi TO search_app;
GRANT SELECT ON ALL TABLES IN SCHEMA susi, jungsi TO search_app;
-- 향후 새 테이블도 자동 SELECT 허용
ALTER DEFAULT PRIVILEGES IN SCHEMA susi   GRANT SELECT ON TABLES TO search_app;
ALTER DEFAULT PRIVILEGES IN SCHEMA jungsi GRANT SELECT ON TABLES TO search_app;

-- 4) 벡터검색 확장 (search 스키마 인덱싱용)
CREATE EXTENSION IF NOT EXISTS vector;
```

**검증 (권한이 의도대로인지 반드시 확인)**
```sql
-- search_app으로 재접속 후:
SELECT count(*) FROM susi.ss_admission;     -- ✅ 되어야 함
SELECT count(*) FROM jungsi.js_admission;   -- ✅ 되어야 함
INSERT INTO susi.ss_admission(name,year) VALUES('x',2027); -- ❌ permission denied 나야 정상
```

- [ ] dev에서 권한 부여 + 검증
- [ ] prod에서 권한 부여 + 검증
- [ ] `search_app` 비밀번호를 검색앱 `DATABASE_URL`(Secret Manager 권장)에 등록

> 참고: 이 권한이 곧 multiSchema의 "강결합" 안전장치다. 코드가 실수로 써도 DB가 거부한다.

## ② Hub 앱 등록 (SSO 연동 전제)

검색앱은 Hub가 발급한 JWT로 로그인을 처리한다(자체 인증 없음). 방식 A(위성앱 토큰교환, 권장) 기준 필요 작업:

- [ ] **Hub `hub_apps`에 검색앱 레코드 추가** (`id`, `name`, `app_url=검색앱 프론트 URL`, `is_active=true`)
- [ ] **Hub Frontend에 `VITE_SEARCH_URL` env 추가** — 이게 없으면 Hub가 검색앱용 `sso_code`를 생성하지 않음
- [ ] **`AUTH_JWT_SECRET`(Base64) 공유** — 검색앱 백엔드에 동일 값 주입(검증용). **포맷·값 변경 절대 금지**(변경 시 전 생태계 세션 무효화)
- [ ] (선택) 서버-서버 호출이 필요하면 **서비스 토큰 발급**: Hub-Backend `scripts/issue-service-token.ts --service search`, 검색앱은 `X-Service-Id: search`로 `/api/internal/*` 호출
- [ ] (대안 방식 B, OAuth2 표준 채택 시) `hub_apps` 대신/추가로 **`oauth_clients`에 등록**(`clientId`, `redirectUris`, `allowedScopes`)

> 누가 실행? Hub 레포/인프라 관리자(=본인). Hub-Backend·Hub-Frontend 양쪽 설정.

## ②-b Hub "입시 프로파일" API 구현 (개인화 레이어 — Hub 소유로 확정)

검색앱·배달앱이 공유할 통합 프로파일을 **Hub가 소유**한다(2026-06-29 결정). Hub 측 신규 작업 필요.

- [ ] **엔드포인트 구현**: `GET /api/internal/users/:hubUserId/admission-profile` (`ServiceAuthGuard` + `X-Service-Id`)
- [ ] **소스 종합**: 생기부(Hub) + 생기부분석(생기북) + 모의분석(모고) + 수시분석(susi `ss_user_*`/`susi_*_tb`) + 정시분석(jungsi `js_user_*`) + 교육과정(`hub_2015/2022_kyokwa_subject`)
- [ ] **응답 스펙 합의**: `curriculum`, `grade`, `naesin_summary`, `csat_mock_summary`, `saenggibu_summary`, `susi_fit_signals`, `jungsi_fit_signals` (기획서 §4.5)
- [ ] **생기북·모고 분석결과 테이블 위치 확인** (스키마명/테이블) — Hub가 읽을 대상
- [ ] 검색앱은 이 API만 소비(소스 직접 읽지 않음). 전형 데이터만 multiSchema 직접 읽기.

> 검색앱 착수와 병행: Hub API가 준비 전이면 검색앱은 mock 프로파일로 개발 진행 가능.
